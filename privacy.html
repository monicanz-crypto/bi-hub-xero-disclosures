Xero integration privacy notice

Operator and purpose

This private integration is operated by Monica Ferguson for her own business administration. Monica is the only intended user.

Information processed

During the one-shot connection process, the integration temporarily processes in memory:

  • the OAuth authorization response, authorization code, access token, and ID token;
  • identity claims associated with the openid, profile, and email permissions;
  • the granted scope list;
  • connection metadata returned by GET /connections, including the tenant type and the tenant and connection identifiers required to validate the organisation and request deletion of the exact connection; and
  • provider status and error information required to fail safely.

The minimized result contains only status, tenant type, exact granted scopes, and accountingDataRead: false. It does not output a raw or hashed tenant identifier. No Accounting API endpoint is called in the initial flow. accounting.settings.read is a permission, not evidence that an Accounting API endpoint was called.

Storage, security, and retention

App credentials and the dedicated database logger credential are stored in macOS Keychain. The database security-event log contains only a fixed, data-free event taxonomy and never contains OAuth tokens, ID tokens, identity claims, authorization codes, callback URLs, provider URLs, tenant or connection identifiers, tenant or organisation names, connection metadata, provider payloads, accounting data, personal data, or provider error text.

The private Hub database assigns each timestamp and sequence, maintains a separate head and HMAC-SHA-256 chain, and permits the dedicated logger credential to execute only the exact append routine. That credential cannot select, insert, update, delete, or truncate the underlying tables. The design does not claim administrator-resistant WORM storage: a Supabase project owner or database administrator can ultimately override database controls.

The security-event chain is retained for at least 400 days after its maximum server-assigned event timestamp. There is no application delete route or automatic retirement. An incident, legal hold, investigation, or unresolved anomaly extends retention. Selected rows are never deleted or rewritten; any eventual whole-chain retirement requires a separately controlled database change.

The integration requests deletion of the exact Xero connection after validating the inventory. A successful request returns HTTP 204, which documents that Xero has deleted the connection; there is no separate post-deletion GET /connections readback. If the deletion request is not accepted, the flow fails and deletion remains unconfirmed, so the connection may remain. Connection deletion is not token revocation, and the unpersisted access token may remain valid until expiry, which is up to 30 minutes.

The integration does not sell personal information or Xero data and does not share Xero data with advertisers or data brokers.
